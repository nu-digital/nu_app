## 2. 開発の進め方（なぜこの方式か）

- **小さいIssue・PR・実行可能なチェック・CI**: 1 Issue = 1 PR。マージの前に、その最新コミットでCI（14のジョブ）が全部成功していること。「テスト成功」は実際に実行した結果で主張する。
- **AIエージェント（Claude Code）が主に実装し、人が判断・承認する**: 仕様の未確定部分は勝手に確定せず[DECISIONS](DECISIONS.md)に提案として残す。本番へのデプロイは、mainへのマージ後にGitHub Actionsが動き、**運用責任者がGitHubの環境`production`で承認**したときだけ。手動SSHで本番を変えることを通常の手順にしない。
- **コストと権限の線引き**: 開発作業はClaude Teamの内包使用量だけを使い、追加課金・APIへの切り替えをしない。例外として、ぬるの**実行時**のAPI利用だけは、月$60（Teamプラン付属のクレジット）の範囲で許可（[CLAUDE_TEAM](CLAUDE_TEAM.md)）。開発・CI・テストでは実際のClaude APIを呼ばない。
- **実機でしか分からないことは、先に推測で確定せず、実機で確認して記録する**（[RUNBOOK §13](RUNBOOK.md)）。

## 3. 主な設計判断とその理由

| 判断 | 理由 |
|---|---|
| **単一VPS（4GB）・Docker Compose・ホストのNginx** | 約20人の団体に対して過剰な構成（Kubernetes・マイクロサービス・別の認証サーバー等）を避ける。運用担当が代替わりしても読める構成にする |
| **認証・権限はすべてGo APIに集約**（UIの非表示だけで制限しない）。認可表をテストで全エンドポイントと突き合わせる | 権限漏れの防止。個人情報と活動履歴を持つ本番サービスだから |
| **公開サイトは公開版のAPIだけから描画**。下書きは返さない（テストで検査） | 下書き・個人情報の漏えい防止（D01・D08・D14） |
| **画像はGitに入れず永続ボリュームに保存**、非公開と公開を分離、再エンコード・上限（D06） | アップロード画像の攻撃対策・個人情報の保護 |
| **既存サイトの見た目・URLを維持**（Git履歴ごとsubtree移設・移設前基準との比較を常時実行。D11・D13） | 既存の公開サイトを壊さずに引っ越すため |
| **DBはPostgreSQL 18 + pgx + goose（前進のみのmigration）+ sqlc** | 実績・型安全・単純さ。切り戻しは「前の版が新しいスキーマでも動く」ルールで担保 |
| **通知（Discord）はoutbox経由**で、Discord障害で業務操作をロールバックしない | 通知は付随機能。業務を止めない（P2-04） |
| **バックアップはVPS内に毎日・7世代**、DBとメディアを一組、復元を隔離環境で検証（D04） | 初期スコープでVPS外は対象外（運用責任者の判断。VPSを失うと復旧できない点は既知の制約） |
| **ぬるは別サービス・別スキーマ・別ロール**（nu_app本体のテーブルを読めない） | 影響範囲の分離。AIの暴走・乗っ取りが本体データに及ばないように |
| **ぬるの安全はプロンプトでなくコードで守る**（許可リスト・Adminロール照合・予算・上限・公開/非公開・忘れる処理）。入力はすべて「データ」として囲む | プロンプトインジェクションや想定外のモデル挙動に対して、コードの境界で止める |
| **ぬるの予算は段階制御＋Console側の上限＋支払い方法なし**の三重 | 追加課金を絶対に起こさない |
| **ぬるの人格は「説明・演出」でなく言動に滲ませる**（NUL-14） | 設定を演じる不自然さを避ける。禁止フレーズの列挙ではなく、方針の組み替えで調整 |

## 4. 運用で学んだこと（同じ失敗を繰り返さないために）

- **CIのNginxと本番のNginxを同じ版にそろえる**: 本番のNginx 1.24では`http2 on;`が使えず、実機で初めて分かった（RUNBOOK §4）。
- **DBバックアップにはロールが含まれない**: 復元先で先に`infrastructure/backup/roles.sql`を実行する。`ALTER DEFAULT PRIVILEGES`・`ALTER ROLE ... SET`はmigrationに書かない（復元・並行テストで壊れる）。CIの`ops / backup-restore`が検出した。
- **並行して動く処理の競合はDBで原子的に**（`FOR UPDATE SKIP LOCKED`・advisory lock・`ON CONFLICT`）。リマインダー・上限・予算で採用し、並行テストで確認した。
- **「一度きり」の外向きの動作は、先に記録してから実行**（挨拶・週報・日誌など）。失敗しても繰り返して費用や投稿が増えない。
- **文書の機械的な編集は、置換が実際に起きたことを確認する**: 過去に、スクリプトの編集ミスでREADME.mdが空になり、気づかれないまま残っていたことがある。編集後は差分を必ず見る。
