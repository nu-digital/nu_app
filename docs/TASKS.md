# nu_app 実装計画・受け入れ条件 v0.1

## 開発ルール

- **各タスクを独立してレビュー可能なPull Request**に分割。マージ後の本番自動デプロイが予定されるため、未完成機能は表示しないか機能フラグで無効化する。
- 重要なセキュリティ、外部連携、DB変更は設計・テストとセットで実装する。
- 本番データをローカルに持ち込まない。デモは完全な架空データを使用。
- 初期ユーザー・物品データの一括移行は不要。公式サイト記事・画像の一度きりの移行は必要。

## P0: モノレポ初期化・既存サイト整理

- [ ] 新規モノレポを作成し、`apps/web`に現行公式サイトをGit履歴をなるべく維持して取り込む。
- [ ] 今のソース・表示・記事・画像をローカルで再現し、スクリーンショット/スナップショットを比較基準として保存。
- [ ] `apps/admin`, `services/api`, `services/bot`, `db`, `infrastructure`, `docs`を用意。
- [ ] Go toolchain, Node/npm workspace, sqlc/pgx, migration toolのバージョンを固定。
- [ ] 移設は`git subtree add`で履歴を維持（squashしない）。P0-01と同じlockfileで移設後、依存更新（next/eslint-config-next/Playwright等の固定、audit対応）を直後の独立PRでP0中に実施（D11/D13）。
- [ ] Docker ComposeでローカルNext.js/Go/PostgreSQLを起動可能にする。
- [ ] `.env.example`, `.gitignore`, 開発手順、CIワークフローを追加。

**受け入れ:** 新規PC上でREADMEに沿って起動できる。既存サイトの主要ページが移行前と同等に表示される。秘密情報がGitに含まれない。

## P1: 認証・権限・ランチャー

- [ ] DB migrations: users, credentials, sessions, tokens, roles, audit, profiles（必須は表示名のみ。公開同意は別テーブル）。
- [ ] Owner継承の二段階フローと緊急復旧管理CLI（セッション失効・監査）。
- [ ] 初期OwnerのCLIによる単回bootstrapと再実行禁止。
- [ ] Adminによるユーザー作成・招待リンク生成・再発行。
- [ ] 招待リンクの期限切れ、使い回し、失効後アクセスを拒否。
- [ ] ID/Passwordログイン・ログアウト・パスワード再設定。
- [ ] セッションCookie・CSRF・入力検証・ログインレート制限・ロール判定。
- [ ] AdminによるMember発行とEditor管理。OwnerのみAdmin付与/解除可能。
- [ ] アカウント停止後のセッション強制失効。
- [ ] 共通アプリランチャー、PC/スマホレスポンシブ、プロフィール初期画面。
- [ ] PR CIとmain自動デプロイの基盤・ヘルスチェック。

**受け入れシナリオ:**
1. 空のDBにCLIでOwnerを1人作成でき、初回bootstrapを2回目に実施できない。
2. AdminがIDを発行、本人がワンタイムリンクからパスワードを設定してログインできる。
3. Memberが管理者APIを直接呼ぶと403。AdminがOwner専用APIを呼ぶと403。
4. Ownerが最後のOwnerを解除しようとしても拒否される。Owner継承は、申請(24時間)→移譲先の承諾で1トランザクションで確定し旧OwnerはAdminに残る。取消・失効・同時承諾が整合し、緊急復旧は管理CLIのみで公開Web入口がない。
5. アカウントを停止すると、すべての既存セッションが使えなくなる。
6. PCとスマホで全員同じランチャーカードが表示される。

## P2: メンバー・物品管理

- [ ] プロフィール編集・公開設定。私的項目は本人とAdmin/Owner専用レスポンスのみ。
- [ ] 表示名・アバター・外部リンク・個人機材の登録と公開制御。
- [ ] メンバー一覧、表示名検索。退会/卒業者は現役一覧から非表示。
- [ ] Adminによる個人情報手動削除と監査ログ。
- [ ] 物品写真付き一覧/検索/カテゴリ/詳細。Adminの数量/個体登録。
- [ ] 数量・個体双方での貸出と代理返却、残数・日数・履歴。
- [ ] 二重貸出防止・部分返却・貸出中の廃止禁止。
- [ ] Adminによる誤記録修正と理由の記録。
- [ ] Discord Bot設定画面。貸出・返却の毎回通知、出力失敗時の再送。

**受け入れシナリオ:**
1. 5本のHDMIケーブルをAが2本、Bが3本借りると残0本になり、それ以上は借りられない。
2. 残1本に2人が同時に貸出要求しても、成功は1件だけ。DB履歴が矛盾しない。
3. Aが借りたものをBが返却した場合、borrower=A、return_actor=Bを表示。
4. 数量管理の2本貸出から1本だけ返却でき、未返却は1本。
5. 個体管理の同じPICO個体を二重貸出できない。
6. 非公開の学年・所有機材・氏名・学生証番号・メールが一般ユーザーAPIから取得できない。
7. Discord APIを意図的に失敗させても貸出記録は確定し、再送処理できる。

## P3: CMS・公式サイト移行

- [ ] CMSのcontents/revisions/collaborators/contributors/media schemaを追加。
- [ ] 下書き作成・保存・競合検知・共同編集者指定・公開・非公開化。
- [ ] 作品へ複数メンバーの役割登録、プロフィール実績への連動。
- [ ] VPS保存の画像アップロード（D06: JPEG/PNG/WebP、上限・寸法検査・縮小・再エンコード・EXIF除去）。下書き非公開と公開画像の境界・画像の参照整合性。既存画像はこの制限で変換せず移設。
- [ ] 既存Markdown(frontmatter)/画像の移行スクリプト。再実行しても重複作成しない。
- [ ] 既存サイトのURL/デザインを維持して公開コンテンツAPI対応。
- [ ] 公開版がCMS公開後にサイトへ反映。下書きは公開サイトからアクセス不可。
- [ ] Markdownの危険なHTML/URL/埋め込みをサニタイズ。

**受け入れシナリオ:**
1. Memberが作成した下書きは本人と共同編集者、Editor/Adminのみ編集できる。
2. Memberが直接publish APIを呼んでも403。Editorが公開するとサイトへ反映。
3. 公開済み記事に編集を保存しても、再公開まで旧版が表示される。
4. 同じ記事を2人が古いrevisionから保存すると後の保存は409で止まる。
5. 未公開画像URLを匿名ユーザーが開いても閲覧できない。
6. 既存`/blog/.../`, `/news/.../`, `/project/.../`の主要URLを維持（大文字・ドット入りslugを含む）。
7. 公開作品へ参加したメンバーのプロフィールにその作品が表示される。公開同意のないクレジットは公開サイトに露出しない。
8. 公開同意を撤回/個人情報を削除すると、公開版・キャッシュ・古いrevisionでも「退会メンバー」等の匿名表示になり、内部の関連・履歴は残る。
9. YouTube URLのみが埋め込まれ、生のiframe/script/videoは拒否され、既存11記事のYouTube表示が維持される。
10. 部分日付（年月のみ・期間・日付不明）は原文どおり表示され、並び替え用に補った日は開催日として表示されない。

## P4: 運用仕上げ（各Phaseで逐次着手）

- [ ] main mergeでのイメージビルド・VPS pull/deploy・healthcheck。
- [ ] 失敗時のDiscord通知と前版イメージへの切り戻し手順。
- [ ] VPS内バックアップ（D04: 毎日03:00 JST・成功7世代・DB+メディアを一組・失敗通知・既存世代を失敗で消さない・隔離環境での復元検証・容量実測）。日次で最大約24時間分を失い得ること、VPS喪失時は復旧不可を運用文書へ明記。
- [ ] HTTPS（Nginx正式採用・証明書の自動更新と失敗検知、D03）、Firewall、secret管理、ログの個人情報マスキング。
- [ ] 4GB VPSでサービス同時起動のメモリ/CPU/ディスク使用量を測定。
- [ ] 移行前後の公式サイト表示・リンク・画像を検証。
- [ ] 管理者向け運用手順: ユーザー発行、Owner引継ぎ、DB復元、デプロイ復旧。

## 完成判定の共通DoD

- [ ] 定義されたAPI・DB migrations・権限テストが実装されている。
- [ ] 関連する回帰テストがCIにあり成功する。
- [ ] エラー時のユーザー表示と操作ログがある。
- [ ] マイグレーションが空DBで適用・再適用安全性を検証済み。
- [ ] デプロイ後に/healthzと主要な画面を確認できる。
- [ ] ブランチに未承認の本番データ・token・パスワード等をコミットしない。
