## 2. フロントだけで開発する構成案

初回はGitとリポジトリ指定のNode/npmで、対象アプリにだけ `npm ci` を実行する。次の2コマンドをルートに追加する案。**どちらも現時点では未実装**。

| コマンド案 | 起動するプロセス | 開発者が確認する画面 |
|---|---|---|
| `npm run web:dev` | 既存の公開HTTPモック ＋ webの `next dev` | トップ・一覧・記事・作品・ギャラリー |
| `npm run admin:dev` | 架空データを返す内部HTTPモック ＋ adminの `next dev` | ログイン後のホーム・メンバー・貸出・CMS。起動引数でロールとシナリオを選ぶ |

Nodeの起動スクリプトから各アプリのNext CLIへ引数を渡す。シェル固有の環境変数代入やバックグラウンド記号に依存させない。Nextとモックはループバック限定、アプリごとのポートで同時起動可能にする。モックを先に起動して応答を確認し、Nextの**子プロセスだけ**に `API_INTERNAL_URL` を設定する。ポート使用中なら対象を表示して終了し、Ctrl+C・子プロセス異常終了後には両方停止し、同じコマンドで再起動できることを3 OSで確認する。

### モックを置く場所と選択理由

- **第一候補は別プロセスのNode HTTPサーバー。** webにはすでにループバック限定の [公開モック](../scripts/mock-public-api.mjs) があり、adminも既存のrewriteの中継先を変えれば実際のAPIクライアント・Cookie・CSRFの経路を通る。新しい常駐サービスや開発用ログイン画面を配備する必要がない。
- **MSW** はコンポーネント単体の通信状態をStoryごとに切り替える場合の候補。ブラウザーのService Workerが扱えるのはブラウザーの通信。webのサーバー側fetchも扱うにはNode側にもハンドラーを登録する必要があり、初期導入の費用が大きい。[MSWのNode統合](https://mswjs.io/guides/integrations/node)
- **Playwrightのルート差し替え**はブラウザーテストに限定され、普段使うブラウザーから自由に操作する入口にはならない。**Compose＋Go API** は書き込みの整合性・認可・実画像の配信を確認する既存の結合環境として使う。

### 画面で再現するシナリオ案

| 対象 | 最初に用意する状態と観察点 |
|---|---|
| ログイン・ホーム | 匿名の `/auth/me` は401。架空のログインでローカル専用Cookieを発行し、再読込・ログアウトも確認。Member / Editor / Admin / Ownerで同じカードを表示し、遷移先の403や編集・公開操作の差が見える。自動フィードの架空APIは作らない |
| メンバー・プロフィール | 架空の本人／他人、任意項目の未入力、公開同意の有無、検索0件、次ページ。写真と表示名の例に実在メンバーの非公開データを使わない |
| 物品・貸出 | 数量管理／個体管理、全数貸出中、自分と他人の貸出、部分返却。メモリ内で変更後の再読込に反映。競合・二重操作の表示も確認する |
| 記事・作品 | 作業版と公開版を分け、Memberの編集範囲とEditorの公開操作、保存時の409、未公開URLの404、公開クレジット撤回後の匿名表示を確認する |
| 各一覧・フォーム | 同じデータを通常・空・応答遅延・失敗で切り替える。読込表示、再試行、入力保持、二重送信防止を見る。401・403・409・429・5xxは対象ルートの実契約に合わせる |

固定ID・固定時計・再起動で初期化するメモリ内データを使う。モックは `scripts/` 配下に置き、両アプリの配布コンテキスト外で起動する。アプリにモックのimport、公開環境変数による認証切替、Service Workerの配布を追加しない。開発ランチャーは明示したローカル宛先だけを渡し、未定義ルートはエラーにする。実APIへのフォールバック、外向きの転送、実アカウント・本番の環境ファイルの読込みを設けない。シナリオ用のCookie・CSRF値はローカルの一時セッション専用とする。

### 契約の乖離をどう検出するか

1. 最初に対象画面のmethod・path・status・必須項目を [API](API.md) とGoハンドラーから拾う。adminの `Me`、`Member`、`ItemDetail`、`ContentDetail` 等をfixtureの型検査で参照する。webは表示用 `ContentPost` と公開APIのwire型が異なる。必要なら既存の `ApiItem` / `ApiDetail` を型だけ取り出し、モック専用の型の複製を避ける。
2. 同じリクエストと期待する形を、ローカルモックと使い捨てCompose上のGo APIに順に当てる。成功時だけでなく、`nextCursor` の終端、401/403のエラー本体、更新時のCSRF、CMSの `baseRevision`、公開応答に作業版・内部IDが入らないことを比較する。IDやトークンの実値は比較・保存しない。
3. 既知の差がある。公開モックは移設記事の本文・並びを再現するが、`date.kind` を一律 `exact`、`sortDateIsEstimated` を一律falseとし、アップロード画像の公開ルートも実装しない。実APIの日付種別は `day/month/range/unknown`。日付のゴールデンで部分日付を検証し、公開画像が必要なStoryには架空画像を明示する。モックの成功を境界の合格判定に使わない。[モック](../scripts/mock-public-api.mjs)・[移行用の日付基準](legacy-baseline/dates.json)
4. 実装PRのCIでモック・fixtureが本番standalone・静的ファイルに含まれないこと、通常起動にモック用ルートがないこと、API遮断時に架空データを返さないことを検査する。既存のGo統合テスト・Compose E2E・公開サイトの比較も通す。

## 5. Issue・PRへの分割案

各行は1 Issue / 1 PRの候補。上の行から取り組み、契約変更が必要になった時点で別のAPI・DB案件として判断する。

| 順序 | 目的と依存 | PRの受け入れ条件 |
|---|---|---|
| 1 | 公式サイトの単体起動を1コマンド化 | 新規clone・webの依存だけで記事とギャラリーが開く。3 OSで起動・編集反映・終了・ポート再利用を確認。起動時にNextが生成するローカルファイルの扱いも決める |
| 2 | 同じ起動方式でadminの認証・ランチャーを再現 | 架空ログイン、再読込、ログアウト、4ロールの同一カードと権限不足。両アプリが同時起動でき、通常ビルドへの混入検査と最小の実API契約比較が通る |
| 3 | メンバー一覧・詳細を追加（2の認証を利用） | 本人／他人・未入力・絞り込み・遅延・0件・失敗を切り替え、実APIの可視フィールドと一致 |
| 4 | 物品・貸出を追加（2に依存） | 一覧→貸出→部分返却後の数量、競合・再試行を再現。実在庫の整合性を検証する既存統合テストも通る |
| 5 | CMSと公開表示を追加（1・2に依存） | 編集・公開・撤回・409のStoryまたは操作例。公開と下書きが分離し、公開モックの日付種別を実API・ゴールデンと照合 |
| 6 | adminのトークン・基本部品を既存の1画面で使用（2を利用） | ボタン・入力・通知を再利用し、PC・スマホ・キーボードの証跡を残す。CSS単独と候補ライブラリの導入差分から採否を記録 |
| 7 | 部品カタログを試行（6に依存） | Storybookのローカル起動・静的ビルド、代表的な異常状態のStory、次の担当者が部品を探して再利用できる例。導入コストが見合わなければDESIGNの使用例を継続 |
