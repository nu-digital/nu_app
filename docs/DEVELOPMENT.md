# 開発とGitHub運用

## 基本

`main`を唯一の統合ブランチとする。長期のdevelopブランチは作らない。1 Issue / 1目的 / 1短命ブランチ / 1 PRを基本に、動作・テスト・必要なmigrationと文書を一緒にレビューする。

ブランチ: `<type>/<issue番号>-<kebab-case>`。
typeは `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`。
例: `feat/12-invite-acceptance`, `test/24-concurrent-loans`。
最初の準備だけ `chore/bootstrap-agent-harness` を例外とする。

コミットとPRタイトル: `<type>(任意のscope): 日本語の変更内容`。
例: `feat(auth): 招待URLの使い回しを拒否する`、`docs: 物品貸出の受け入れ条件を整理する`。
ブランチ名・識別子は英語、説明は日本語。コミットは一つの変更意図にまとめる。

## 1タスクの流れ

1. mainとIssueを読み、未コミット変更を確認。他人の変更を消さない。担当範囲と依存PRを確認。
2. 新規ブランチを作り、対象要件・影響範囲・DB・API・テスト・切り戻しを6項目で記す。
3. 既存実装とテストを調査。未確定事項は [DECISIONS](DECISIONS.md) に提案・影響・代替案・誰の判断が必要かを書く。
4. 受け入れ条件に沿って小さく実装。バグ修正は可能なら先に再現テストを書く。
5. 準備用チェックと変更対象のテストを実行。差分を読み直し、不要ファイル・秘密値・仕様逸脱を点検。
6. 日本語コミット、作業ブランチへpush、PR作成（未完ならDraft）。本文に `Closes #番号`、実測結果、未実施を記載。
7. PRの最新コミットのCIを確認し、失敗は修正して再確認。画面変更は操作確認と画像比較、DB変更はPostgreSQLで検証。
8. **マージの運用**: 2026-11-21の指示で、PR #28以降は運用責任者のレビューを待つ運用になった。ただし**ぬる（`services/agent`）の開発（2026-11-26〜）では、運用責任者の指示のもと、PR最新コミットのCI全成功を確認したうえで、AIが自律的にマージした**（本番デプロイの承認は常に人）。今後の方針（自律マージを続けるか）は運用責任者が決める。Squash mergeのタイトルも日本語。履歴維持が必要な移設はmergeコミット。マージ後は最新mainから始め、依存PRはマージ待ちの間は積み重ねてよい。

環境不足は成功に数えない。無関係の作業は進め、問題のある受け入れ条件は未完了と明記する。別のエージェントや新セッションは [引き継ぎ](handoffs/TEMPLATE.md) と実際のGit/CIを照合して再開する。

## マージとレビューの運用（2026-11-21 ユーザー指示で更新）

**PR #28までは**、確定仕様内の通常開発についてClaudeが条件付きで自律マージした（#12の指示。PR最新コミットのCI成功・自己レビュー・証拠が条件だった）。**PR #28以降は次のとおり**。

- Claudeが行うこと: 作業ブランチへのpush、Draft PR作成、**PR最新コミットのCI成功の確認**、不具合の修正、引き継ぎの更新。**マージは運用責任者のレビューを待つ**。
- 依存するPRは**積み重ねてよい**（baseを前のPRのブランチにする。前のPRがマージされたらbaseをmainへ付け替える。履歴の途中でbaseがずれて内容がmainに入らない事故に注意し、マージ順をPR本文に書く）。判断待ち・マージ待ちで全体を止めず、独立した作業を進める。
- 引き続き行わないこと: mainへの直接push、force push、保護ルールの緩和、GitHubの自動マージ機能・無人の連続運転、**本番デプロイ・本番データ変更・OS権限変更・追加課金**。
- 運用責任者は、完成後に実際のWebアプリを操作して機能・使いやすさ・デザイン・運用方法を確認し、修正を依頼する。したがって、動作する機能を着実に作り、変更容易性・保守性を保つことを完璧な事前確定より優先する。

### 未確定仕様の扱い

- 正本は`docs/TASKS.md`・`BACKLOG.md`・`DECISIONS.md`などの設計文書。**D01〜D15の確定仕様は変更しない**。
- それ以外の細かな仕様・UI・内部設計は、既存要件との整合を調べて**自律的に決める**。判断が難しいときはCLAUDE_TEAMの方針でOpusに設計・比較させ、通常の実装はSonnetで行う。
- 情報が足りなくても、**安全で後から変更できる仕様**なら合理的な仮定を置いて実装してよい。認証・認可・個人情報・DB整合性は常に安全側にし、必ずテストする。
- 暫定採用した仕様は[DECISIONS](DECISIONS.md)の「暫定採用（ユーザー未確定）」に、**判断理由・代替案・変更時の影響**とともに記録し、ユーザー確定事項（D01〜D15と運用責任者の承認）と区別する。不可逆な変更や重大なセキュリティリスクは推測で実行せず、記録して運用責任者へ知らせる。

## 自律的に決められること

要件内の実装分割、命名、テスト追加、リファクタ、内部UIのレイアウト・余白・状態表示は調査して決めてよい。各選択で許可を求めない。依存ライブラリは既存構成と互換性を確認し、固定バージョンと採用理由を記録する。

未確定の業務仕様・個人情報公開・スコープ拡張は決めない。本番変更、mainへの直接push、force push、保護ルールの緩和は通常の自律作業から除く。初回の初期仕様main登録のみユーザー承認済みの例外。

## GitHub側で設定する項目

初回pushとCI実行後にSettingsで設定・確認する。ファイルを置くだけでは有効にならない。

**2026-11-20実測:** このときはprivateで、main保護の取得APIが「プランのアップグレードまたはpublic化が必要」と403を返し、保護を有効化できなかった。公開範囲や契約は勝手に変更しない。

**2026-11-21実測:** リポジトリはpublic（運用責任者の変更）になり、保護を設定できる状態になった。P0-04でmainのbranch protectionを有効化した（強化であり緩和ではない）: PR必須（承認数0。一人運用）、必須チェック（下記）、force push・削除禁止、会話解決必須、管理者にも適用。解除や緩和は運用責任者の判断。確認: `gh api repos/nu-digital/nu_app/branches/main/protection`。

- デフォルトブランチmain、Squash merge、マージ済みブランチの自動削除。
- mainのRulesetまたはbranch protection: PR必須、force push・削除禁止、会話解決必須、CI必須。管理者の恒常的bypassも避ける。
- 必須チェック（実際のチェック名。2026-11-28確認）: `harness / repository`、`harness / policy`、`web / lint-typecheck-build`、`admin / lint-typecheck-build`、`go / services/api`、`go / services/bot`、`go / docker build`、`go / sqlc`、`go / integration`、`compose / smoke`。必須チェックが未実行のままpendingにならないよう、各workflowは`paths`絞り込みを持たず全PRで実行する（約8分）。新しいチェックを追加したら、名前を保護ルールの必須チェックへ追加する。**注意（2026-11-28）: `go / services/agent`・`ops / backup-restore`・`ops / nginx`・`ops / deploy-script`は、CIでは実行されるが保護ルールの必須には入っていない**（ぬる・運用スクリプトの退行がマージ自体は止めない。デプロイの`verify`は全チェックの成功を待つ）。**PRのチェック一覧で14件すべての成功を、マージ前に必ず確認する**。必須に加えるかは運用責任者が決める（[BACKLOG](BACKLOG.md)）。
- 複数のレビュー担当者がいる場合は承認1件・最新差分で承認失効を設定。一人運用では自分のPRを自分で承認できないため、承認数必須は無理に設定せず手動レビューとCIで運用し、体制を記録する。
- 保護機能が使えない状態（privateでプラン不足等）に戻った場合は、保護済みと呼ばず、制限を明記する。
- Actionsは最小権限。PRのコードに本番secretを渡さない。`pull_request_target`でPRコードを実行しない。
- レビュー担当のGitHub IDが確定したらCODEOWNERSを追加。存在しないチーム名を仮登録しない。

Issueテンプレートは準備済み。実IssueとPRはGitHubを進捗の正本とし、[BACKLOG](BACKLOG.md) は分割と依存関係の地図にする。

Dependabotが作成した専用ブランチのPRだけは自動生成のブランチ名・英語タイトルをCIで例外扱いする。レビュー担当者はマージ時のSquashタイトルを日本語に直す。人のPRにはこの例外を適用しない。

## ハーネスの境界

`CLAUDE.md`はAGENTS.mdを読み込む入口。`.claude/settings.json`のStop hookは終了前に軽量チェックを行う。リトライ無限ループ防止のためhookによる再開中はブロックを繰り返さない。チェック失敗が解決したことを意味しない。

hookは信頼済みプロジェクトのClaude Codeで読み込みを確認する。NodeがPATHにない環境やhook未対応クライアントでは動かないためCIで同じチェックを行う。hookは権限制御・secret scannerではない。独自の常駐エージェント、無制限の自己反復、必須の並列エージェントは導入しない。

参照（2026-11-20確認）: [Claude Codeの推奨運用](https://code.claude.com/docs/en/best-practices)、[指示ファイル](https://code.claude.com/docs/en/memory)、[hooks](https://code.claude.com/docs/en/hooks)、[GitHubブランチ保護](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。
