# nu_app 要件定義 v0.1（エージェント引き継ぎ用・ドラフト）

更新日: 2026-11-15  
状態: **要件ヒアリングに基づく初稿。未決定事項は「要確認」として明記**。

## 1. 目的・設計原則

nu_digitalの団体運営を支える共通ポータル。20人程度での利用を初期規模とし、管理業務を増やさず、今後の予算申請・領収書提出・イベント等のモジュールを追加できること。

- 日常操作は簡単に。物品貸出に図書館のような期限・申請手続きを持ち込まない。
- 権限判定とデータの公開範囲はすべてAPIで強制する。
- 公式サイトと内部アプリは別ドメイン。アプリとコンテンツのデータをGo API/DBに集約。
- 業務データの変更履歴と通知の送信成否を追跡できる。
- 過剰な分散構成を避け、4GBの単一VPSで動くようにする。

## 2. 初期スコープ

### Phase 1: 共通基盤
- Adminが発行した `nu_digital ID` + 本人が設定するパスワードでログイン。
- 管理者がメンバーのアカウントを発行。公開の自己登録受付は設けない。
- 初回のみCLI等の安全な手順でOwnerアカウントを作成。Webサイトに最初に来た匿名ユーザーがOwnerになれる仕様は禁止。
- Admin発行の期限付き・使い捨て招待URLで本人が初期パスワードを設定。
- パスワード紛失時はAdminによる本人確認のうえ、期限付き・使い捨て再設定URLを個別送付。メール自動配信は初期版不要。
- Owner / Admin / Editor / Member。OwnerのみAdminの追加・剥奪、Owner継承を操作できる。Adminはメンバーの発行・停止とEditor付与を担当。EditorはCMS編集・公開権限。Memberは基本操作。
- 表示名・アバターは本人が変更可能。内部UUIDは不変。ログインIDはAdminのみ管理。
- 原神/HoYoPlayのように団体写真を大きく見せるポータル。アプリランチャーは全ユーザーに共通表示し、操作権限は内部機能とAPIで制御。
- 記事・作品公開やシステム更新の情報をダッシュボードへ自動表示。手動のお知らせ投稿は初期版に不要。
- 初期版は2FA無し。ただし適切なパスワードハッシュ、セッション、レート制限、CSRF/XSS対策は必須。

### Phase 2: メンバー・物品・Discord
- 本人がプロフィール（氏名、学部、学科、学年、大学メール、学生証番号、最寄り駅、機材環境など）を登録・更新。
- 表示名・アイコンはメンバー一覧に表示。学部・学科・学年・機材・自己紹介・外部リンク等は項目ごとの本人公開設定に基づきメンバーへ公開。学生証番号・メール・最寄り駅等の機微な項目は本人と権限あるAdmin/Ownerだけ。
- 外部リンク（GitHub、ポートフォリオ等）は本人が複数追加・編集・並べ替え・削除可。個人所有機材は団体貸出物品と区別。
- 卒業・退会はAdminが停止。ログインセッションを無効化し、活動履歴は維持。個人情報は自動削除せず、Adminが必要に応じ手動削除。個人情報削除後も履歴の参照整合性を維持。
- 物品一覧は写真中心・スマホ優先・メルカリ風。検索・カテゴリ絞り込み・詳細画面。
- 物品ごとに **数量管理** と **個体管理** を切替可能。Adminは追加・編集・廃止・数量調整可能。履歴がある場合の切替はデータ整合性を損なわない制限が必要。
- Memberは承認不要で貸出・返却を登録。誰でも他人の借用品を返却登録可。貸出者・返却登録者・日時・数量を保持。
- 返却予定日、期限、延長申請、QRコードは実装しない。代わりに経過日数を表示。
- 貸出・返却操作のたびにDiscordの専用チャンネルに通知。Adminは重要イベント種別ごとにON/OFFと送信チャンネルを設定可能。通知失敗によって業務操作が失敗しない。
- 通知対象候補: 貸出、返却、記事・作品公開、メンバー登録、障害、デプロイ失敗。通知内容に機密情報を含めない。

### Phase 3: CMS・既存公式サイトのVPS移行
- 既存公式サイトのデザイン、ページ構成、主要URL、既存記事と作品をできる限り維持。
- CMS対象は記事と作品紹介。その他の固定ページは初期CMS対象外。
- すべてのMemberが下書き作成可。作成者は記事ごとに共同編集者を指定可。Editor/Adminは全記事を編集・公開・非公開化可。
- 下書き保存と公開操作は分離。公開中の版を編集しても、再公開までは従来の公開版が表示される。
- Markdown本文、タイトル、説明、画像、URLスラッグ、カテゴリ等を管理。保存競合検知、編集履歴、公開履歴。
- 作品に複数の制作メンバーを関連付け、役割を記録。本人のプロフィールに制作実績を表示。公開サイトへのメンバー名の掲載は本人の公開許可を尊重。
- 画像はVPSの永続領域に保存・配信。非公開画像と公開済み画像を確実に分離する。
- コンテンツ公開はGitHubへMarkdownをcommitする方式ではなく、VPSの公開サイトから公開版を直接配信する。
- 既存のメンバー・物品データは移行ツールを作らず、管理画面から手動登録。既存記事と画像には一度限りの移行手段を用意する。

## 3. ドメイン・運用
- 取得予定ドメイン: `nu-digital.jp`（取得済みとは扱わない）。公式サイト `https://nu-digital.jp/`、アプリ `https://app.nu-digital.jp/`。
- Ubuntu系VPSを想定、初期メモリ4GB、Docker Compose、GitHub Actions。Go API、2つのNext.jsアプリ、PostgreSQL、Discord Bot、リバースプロキシを同居。
- リバースプロキシはNginxを有力候補とするが、ユーザーによる正式な最終確定はまだ。HTTPS必須。
- 新規GitHubモノレポへ公式サイトコードを移設。`main`にマージするとCI成功後に自動デプロイ。PRのテストを必須とする。
- ローカル・エージェント環境で開発し、VPSは本番専用。初期版にステージングは作らない。
- VPS外バックアップは初期版に設けない。VPS故障・ディスク喪失時のデータ喪失リスクを明記。VPS内定期バックアップの実施頻度・保持日数は未確定。

## 4. 初期スコープ外
- 予算申請、領収書提出、会計、イベント・プロジェクト管理の業務機能（後から追加可能な設計に留める）。
- 2FA、QRコード、貸出承認、返却期限、会計連携、メール送信、ステージング、VPS外バックアップ。
- メンバー・物品の一括インポート。
- Google Docsのようなリアルタイム共同編集。

## 5. 個人情報に関する留意点
- 学生証番号・大学メール・氏名・最寄り駅はアプリ外のログ、Discord通知、Gitリポジトリ、一般メンバー用APIへ漏らさない。
- 必須収集項目は最小化し、未入力・非公開でもサービスの主要機能が使えるようにする（詳細は別途確定）。
- 保存後の手動削除機能では監査証跡を残しつつ、削除した個人情報の値そのものを監査ログに保存しない。
- 現状は外部バックアップを作らないため、個人情報・画像・記事の不可逆な消失リスクを利用開始前に運用責任者へ共有する。

## 6. 要確認の主要項目
1. 作品紹介CMSの権限を記事と完全に同じとするか（本書では同じ実装を暫定提案）。
2. 学部・学年などのプロフィール各項目の必須/任意と公開設定の初期値。
3. Nginx正式採用、ローカルバックアップの頻度/世代数。
4. Owner継承時の承諾フローと緊急復旧手順。
5. アバター・物品写真・記事画像のアップロード上限値。
