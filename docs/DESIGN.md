# UI調査とデザインの進め方

公式サイトは既存の団体カラー `#004aad`、ページ構成、URL、本文・画像・ギャラリーを維持する。内部アプリは団体写真を大きく使うランチャー、写真中心・スマホ優先の物品管理を基点に、担当者が既存部品から具体化する。共通部品・ライブラリ・カタログの検討状況は [フロントエンド開発計画](FRONTEND.md) を参照する。

## デザイン原則（第2フェーズ以降。全体）

**ホーム画面は魅力的に、操作画面は直感的に、制作画面は集中しやすく。** 業務管理システム・SaaSの管理画面にせず、**Steamのようなゲームランチャーの世界観**と、**BOOTH・note・メルカリの分かりやすい操作性**を組み合わせる。クリエイターが集まる団体なので、情報を管理するだけでなく、活動やメンバーの作品に触れて制作意欲が湧くポータルにする。

| 画面の種類 | 例 | 優先 | 作り方 |
|---|---|---|---|
| ホーム | ランチャー | 魅力・世界観 | 大きな写真・作品画像、タイポグラフィ、アイコン、モーションを積極的に |
| 操作 | 貸出・返却、設定、メンバー | 分かりやすさ・操作の少なさ | 装飾より状態の見やすさと「次にやること」。確認手順を減らす |
| 制作 | 記事・作品の編集 | 集中 | メタ情報は上にたたみ、本文とプレビューに広さ。余計な表示を出さない |

- 全画面を同じカード／管理画面のテンプレートにしない。画面の目的に合うレイアウトを選ぶ。
- 開発者・DBの都合（版番号・内部の状態・権限の構造）を画面に出さない。不要なページ・ボタン・確認は消す。
- 同じ機能には、どこでも同じアイコン（`lib/features.ts`）。状態は色だけで伝えない。
- **モーション**: 短く自然に・操作を待たせない・`transform`と`opacity`だけ・`prefers-reduced-motion`で動きをやめる。時間は `fast 120ms / base 200ms / slow 360ms / hero 800ms`、イージングは `--ease-out`・`--ease-in-out`（`lib/motion.ts` と `app/ui.css`）。ページ遷移はCSSの短いフェードイン（View Transition APIは、Next（App Router）での安定性とブラウザー差のため使わない）。Motionは出入り・並べ替え・ヒーローに限る。詳細は [design/ui-overhaul-2.md](design/ui-overhaul-2.md) §0・§3。

## 画面を作る前の調査

1. 対象操作と利用場面を定義する。例: 部室でスマホから物品を探し、数量を選び、貸出登録する。
2. 現在公開されている日本語サービスを2〜3例調べる。候補はメルカリの検索/商品写真、SmartHRのフォーム/エラー、デジタル庁のアクセシビリティ。（内部ポータルの調査結果は[design/p1-04.md](design/p1-04.md)に記録済み。新しい画面では同じ手順で調べる）候補を「日本の主流」と断定せず、実際に確認できた画面と適用理由を記録する。
3. `docs/design/<issue番号>.md` に確認日・URL・確認できた範囲・参考にする振る舞い・nu_appへの適用・採用しない点を書く。ログインが必要で見ていない画面は推測として区別する。
4. 情報配置、操作の順序、タイポグラフィ、余白、色、状態表示を決める。ロゴ・写真・画面そのものは無断転載せず、架空データと許可された団体素材で作る。
5. 代表画面を一つ実装し、ブラウザーで確認してから共通部品を広げる。要件内の見た目の選択ごとにユーザー承認を待たない。

調査の出発点: [デジタル庁デザインシステム](https://design.digital.go.jp/dads/)、[SmartHR Design System](https://smarthr.design/)、[メルカリ](https://jp.mercari.com/)。デジタル庁の公開ページは2026-11-20確認。他は実装着手時に該当画面を調査する候補であり、この準備で画面評価済みとは扱わない。

## 管理ポータルの部品の使い方（Charcoal）

管理ポータル（`apps/admin`）の見た目はCharcoal（pixiv・BOOTH）に寄せる。採用の経緯と上書きした値は [design/charcoal.md](design/charcoal.md)。人もAIも、画面を作るときは次の順で部品を選び、その場で独自のボタンや色を作らない。

1. **団体の共通部品** `apps/admin/components/ui/`: `Button`（variant: primary・default・danger、`href` でリンク、並べるときは `fullWidth={false}`、フォームの送信は `type="submit"`）、`TextField`（ラベル必須・onChangeは文字列）、`IconButton`（読み上げ名 `label` 必須）。パスワードは `components/PasswordField`、通知は `components/Notice`。
   - 追加した部品（#186。スタイルは `app/ui.css`）: `Select`・`Textarea`・`Checkbox`（ラベル必須・onChangeは値）、`Badge`（tone: success/warning/danger/info/neutral。**色だけでなく記号と文字**で状態を示す）、`Avatar`・`AvatarStack`（画像が無ければ頭文字。重ね表示、クリックで名前の一覧）、`Dialog`（ネイティブ`<dialog>`。Esc・フォーカス復帰・キャンセル必須）、`useToast`（保存完了などの短い確認。入力の修正が必要なエラーは残る`Notice`）、`Loading`・`CardSkeleton`・`EmptyState`（読込中・空）、`Card`、`SegmentedControl`（表示の切り替え）。
2. **共通CSSのクラス**（`app/globals.css`）: `.page`・`.panel`・`.items`/`.item`・`.badge`・`.notice`・`.field`・`.subnav`・`.actions`。数値・日付・セレクト・テキストエリア・読み取り専用の入力は、ネイティブの要素に `className="input"`（見た目はTextFieldと同じ）。
3. **Charcoalの部品**（[公式Storybook](https://charcoal-web.pixiv.design/)）で足りないものを探し、使うときは `components/ui` に包んでから画面で使う。画面から `@charcoal-ui/react` を直接importしない。
4. それでも無いものだけ、セマンティックなHTMLと上のトークン（`--color-*`・`--radius*`・`--space-*`）で作る。新しい外部ライブラリは採用理由と固定版をTOOLCHAINに記録する。

**画面の作り方（UI/UX改善 #186〜#190で固めた型）**: 一覧は写真・サムネイル中心のカード＋検索＋チップ（絞り込み）、状態は`Badge`（文字＋記号＋色）、読込中は`CardSkeleton`/`Loading`、空は`EmptyState`（次の行動つき）、完了は`useToast`、入力の修正が必要なエラーは`Notice`、確認は`Dialog`（キャンセル必須。`window.confirm`は使わない）、設定は`Row`形式（項目名・内容・公開範囲・変更）、メンバー表示は`AvatarStack`、数の入力はステッパー。物品の状態の判定は`lib/item-status.ts`、記事の日付は`lib/content-date.ts`（ユーザーに内部の日付項目を見せない）。

画面を変えたら `npm run admin:dev:mock`（[LOCAL_DEV](LOCAL_DEV.md)）で、PC・スマホ幅・キーボード操作を確認する。

## 共通の品質基準

- 日本語で短く、何が起きるか分かるラベル。内部の実装用語・HTTPコードだけで説明しない。
- 主操作は見つけやすく、保存中の二重操作を抑止。失敗時に入力を保持し、再試行方法を示す。
- 全員に共通ランチャーを表示。権限はAPIで強制し、遷移後の権限不足を説明する。
- キーボード操作、フォーカス表示/復帰、ラベル、見出し、色以外の状態表現。コントラストはWCAG AAを目標に測定する。
- タップ対象は原則44px以上を目安にし、狭い幅・長い日本語・200%ズームに対応する。
- 空一覧、未検索、読込中、通信失敗、権限不足、競合、部分返却などを「正常系の後回し」にしない。
- 団体写真の可読性、画像の代替テキスト、reduce motion、スマホの通信量を考慮する。
- 色・余白・角丸・文字サイズを共通トークンへまとめる。UIライブラリの追加は採用理由と固定版を記録する。

## PRの証拠

PC/スマホのスクリーンショット、主要操作の確認結果、空/失敗状態、キーボード確認、参照URLと判断理由を添付する。自動アクセシビリティ検査だけで合格にしない。
既存サイトを変える場合は変更前後を並べ、意図した差分を明記する。全面リニューアルは今回の既定方針に含まれない。
