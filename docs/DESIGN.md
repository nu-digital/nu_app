# UI調査とデザインの進め方

公式サイトは既存の団体カラー `#004aad`、ページ構成、URL、本文・画像・ギャラリーを維持する。内部アプリは団体写真を大きく使うランチャー、写真中心・スマホ優先の物品管理を基点に、担当者が既存部品から具体化する。共通部品・ライブラリ・カタログの検討状況は [フロントエンド開発計画](FRONTEND.md) を参照する。

## 画面を作る前の調査

1. 対象操作と利用場面を定義する。例: 部室でスマホから物品を探し、数量を選び、貸出登録する。
2. 現在公開されている日本語サービスを2〜3例調べる。候補はメルカリの検索/商品写真、SmartHRのフォーム/エラー、デジタル庁のアクセシビリティ。（内部ポータルの調査結果は[design/p1-04.md](design/p1-04.md)に記録済み。新しい画面では同じ手順で調べる）候補を「日本の主流」と断定せず、実際に確認できた画面と適用理由を記録する。
3. `docs/design/<issue番号>.md` に確認日・URL・確認できた範囲・参考にする振る舞い・nu_appへの適用・採用しない点を書く。ログインが必要で見ていない画面は推測として区別する。
4. 情報配置、操作の順序、タイポグラフィ、余白、色、状態表示を決める。ロゴ・写真・画面そのものは無断転載せず、架空データと許可された団体素材で作る。
5. 代表画面を一つ実装し、ブラウザーで確認してから共通部品を広げる。要件内の見た目の選択ごとにユーザー承認を待たない。

調査の出発点: [デジタル庁デザインシステム](https://design.digital.go.jp/dads/)、[SmartHR Design System](https://smarthr.design/)、[メルカリ](https://jp.mercari.com/)。デジタル庁の公開ページは2026-11-20確認。他は実装着手時に該当画面を調査する候補であり、この準備で画面評価済みとは扱わない。

## 共通の品質基準

- 日本語で短く、何が起きるか分かるラベル。内部の実装用語・HTTPコードだけで説明しない。
- 主操作は見つけやすく、保存中の二重操作を抑止。失敗時に入力を保持し、再試行方法を示す。
- 全員に共通ランチャーを表示。権限はAPIで強制し、遷移後の権限不足を説明する。
- キーボード操作、フォーカス表示/復帰、ラベル、見出し、色以外の状態表現。コントラストはWCAG AAを目標に測定する。
- タップ対象は原則44px以上を目安にし、狭い幅・長い日本語・200%ズームに対応する。
- 空一覧、未検索、読込中、通信失敗、権限不足、競合、部分返却などを「正常系の後回し」にしない。
- 団体写真の可読性、画像の代替テキスト、reduce motion、スマホの通信量を考慮する。
- 色・余白・角丸・文字サイズを共通トークンへまとめる。UIライブラリの追加は採用理由と固定版を記録する。

## PRの証拠

PC/スマホのスクリーンショット、主要操作の確認結果、空/失敗状態、キーボード確認、参照URLと判断理由を添付する。自動アクセシビリティ検査だけで合格にしない。
既存サイトを変える場合は変更前後を並べ、意図した差分を明記する。全面リニューアルは今回の既定方針に含まれない。
