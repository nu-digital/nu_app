# ぬる 管理画面（nu_app内）設計 v0.1

状態: **設計のみ（未実装）**。運用開始前のレビューで「ぬるの稼働状況・API使用額・エラー・記憶量をnu_appで確認したい」という要望を受けて作成。実装前に、運用責任者の確認が要る点を§8にまとめた。

## 1. 目的と範囲

- 運用責任者・管理者が、**SSHやSQLなしで**、ぬるの「今の状態」「今月の費用」「異常」「記憶の量」を見て、必要なら**止められる**ようにする。
- 見るだけが中心。操作は「全停止／静か／再開」と、変なノートの削除くらいに絞る（日常の操作はDiscordの`/nul`でもできる）。
- **メッセージ本文・ノート本文・DMの内容は、初期版では画面に出さない**（件数・金額・状態・エラーの種類だけ）。個人情報の観点（AGENTS.md）で、見せる範囲は§8で運用責任者が決める。
- 対象外: 一般メンバー向けの表示、ぬるとの会話画面、グラフの凝った分析。

## 2. 設計の前提（既存の境界を守る）

- ぬる（`services/agent`）のデータは`agent`スキーマにあり、nu_app本体のDBロール（`nu_app`）は**読めない**（ロールを分けてある。[ARCHITECTURE](../ARCHITECTURE.md)・NUL-2）。
- 認証・権限は**Go APIに集約**する（AGENTS.md）。UIの非表示だけで制限しない。管理画面のAPIは、既存の**Admin以上**（Owner/Admin）だけが使える。Editor・一般メンバーは403。
- 画面は既存の内部ポータル（`apps/admin`）に、ページを足す形（`/nul`）。

## 3. 方式の比較と推奨

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. agentが内部HTTPで状態を返す | agentに読み取り専用のAPI（Docker内部ネットワークだけ・サービストークン）。Go APIが中継 | agentの内部状態（接続・Tick）が直接見える | **agentが落ちている／無効モードのときに、費用・件数が見えない**。agentに入口が増える |
| **B. 集計だけのビューを共有する（推奨）** | `agent_admin`スキーマに**集計のみのビュー**（本文を含まない）を作り、`nu_app`ロールにSELECTだけ許可。Go APIが読む。agentは定期的に**心拍・イベント**をDBに書く | agentが落ちていても費用・件数・最終の心拍が見える。入口が増えない。バックアップに自然に含まれる | ビューで公開する列を厳密に管理する必要（本文を出さない）。agent側の書き込みが増える |
| C. nu_appロールにagentスキーマ全体を読ませる | 手軽 | **本文・DMが読める**。ロール分離の意味がなくなる | 不採用 |

**推奨はB**。理由: 運用で一番見たい「費用・異常」は、agentが止まっているときこそ必要。公開する列を**ビューで固定**すれば、本文・DMは構造的に出ない（テストで保証できる）。

## 4. データ（agent側に足すもの）

migrationで追加（実装時）:

- `agent.heartbeat`（1行）: `ts`（30秒ごとにagentが更新）・`version`（デプロイのタグ）・`mode`（running/quiet/stopped）・`connected`（Discord接続中か）・`started_at`。
- `agent.events`: `ts`・`kind`（`llm_error`・`llm_credit`・`discord_send_error`・`import_error`・`batch_error`・`budget_stop`・`panic` など固定の種類）・`n`の集計（1時間単位。**本文・ID・エラー文は入れない**）。`ts`は7日で削除。
- 既存の`agent.api_usage`（金額・モデル・用途・チャンネルID・ユーザーID）・`messages`・`notes`・`summaries`・`diary`・`reminders`・`import_progress`・`settings`。

`agent_admin`のビュー（列を固定。本文なし）:

| ビュー | 列 |
|---|---|
| `status` | 心拍の時刻・version・mode・connected・稼働時間・予算の段階（settings・api_usageから計算）・クレジット切れか |
| `usage_daily` | 日・モデル・用途・呼び出し回数・トークン・金額 |
| `usage_month` | 予算期間・使用額・上限・割合・Batch進行中か |
| `memory` | メッセージ件数（公開／非公開／DM別）・ノート件数（公開／private）・要約件数・日誌件数・リマインダー件数・`agent`スキーマのサイズ・取り込み進捗（チャンネル数・完了数）・要約待ちの日数 |
| `events_daily` | 日・種類・件数 |
| `channels` | チャンネルID・公開／非公開・メッセージ件数（名前はDiscordから取れないので、IDだけ。画面ではnu_appの設定のチャンネル名の対応表があれば表示） |

## 5. 操作（書き込み）

- 「全停止／静か／再開」: Go APIが、`SECURITY DEFINER`の関数`agent_admin.set_mode(text)`（`running|quiet|stopped`だけ受ける）を呼ぶ。直接`agent.settings`は書かせない。
- **agentが設定を拾う**: 今のagentは起動時にモードを読むだけ（メモリ保持）なので、**5〜10秒ごとに`control.mode`を読み直す**ように変える（Discordの`/nul`と画面のどちらで変えても同じに効く）。DBが読めなければ**停止側**（既存の安全側の規則）。
- 操作は、nu_app側の既存の**監査ログ**に、操作者・操作・時刻を残す（`/nul`のDiscord側はIDをログに残している）。確認ダイアログ必須。
- 変なノートの削除: 一般のメモ（内省が作る）と、本人のノートの削除を、IDを指定して行う（本文は一覧に出さないので、初期版は「件数と作成日」だけ。内容の確認は必要になったら別途設計）。

## 6. 画面（`/nul`）

1. **状態**: 稼働中／静か／停止（色つき）・最終の心拍（10分以上なければ「オフライン」の警告）・version・接続・稼働時間。ボタン: 全停止／静か／再開。
2. **予算**: 今月の使用額／$60・割合のバー・段階（通常／節約／Opus停止／停止）・月末の予測（直近の日平均から）・用途別（chat・think_hard・web_research・spontaneous・summary_batch・introspect_batch・report・diary）とモデル別の内訳・日別の推移グラフ・クレジット切れの表示。APIキーの期限（`apikey.expires`）と残り日数。
3. **利用状況**: 1日の返答数・Opus数・Web検索数・上位ユーザー（Discord名は`messages`の最新の表示名。IDは出さない／要確認）。
4. **記憶**: 件数（メッセージ公開／非公開／DM・ノート・要約・日誌・リマインダー）・DBサイズと増え方・取り込みの進捗・要約待ちの日数・直近のバックアップのagent行数（`manifest.txt`は本番ホストのファイルなのでAPIからは見えない。表示するなら別途）。
5. **エラー**: 種類別の日別件数（直近7日）。本文は出さない。詳細はVPSのログ（RUNBOOK）。
6. **安全**: 非公開と判定されたチャンネルの一覧（IDと件数。判定がサーバーの権限と合っているかの確認用）。

## 7. 通知（任意・第2段）

既存の共通通知（outbox・P2-04）を使って、次をDiscordの運営向けチャンネルに知らせる: 予算が70%・90%・100%に達した／心拍が10分途絶えた／エラーが急増した／APIキーの期限が14日以内。ぬる自身のtimesとは別の、運営向けの通知（ぬるが止まっていても届く）。

## 8. 実装の段階とテスト

| 段階 | 内容 | テスト |
|---|---|---|
| N-1（agent） | 心拍・イベントの記録、モードの定期読み直し、migration（`heartbeat`・`events`・`agent_admin`ビュー・`set_mode`関数・`nu_app`へのGRANT） | 統合テスト: ビューに本文・DM由来の列が**無い**こと（列名の一覧を固定して検査）、`nu_app`ロールが`agent.messages`を直接読めない・`set_mode`に不正値を渡せないこと、モードの読み直し（DB障害で停止側）、心拍の更新 |
| N-2（API） | `GET /api/v1/admin/nul/status|usage|memory|events|channels`、`POST /api/v1/admin/nul/mode`。Admin以上のみ。監査ログ | 権限の表（Owner/Admin=可、Editor・メンバー・未認証=403/401）、CSRF、不正なmode、レスポンスに本文・IDが出ない（スナップショットに個人情報を入れない） |
| N-3（UI） | `/nul`ページ（§6）。スマホ幅でも読める | 画面の確認（スクリーンショット）、権限のない人にメニューが出ない（出なくてもAPIが拒否する） |
| N-4（通知） | §7 | outboxの試験（Discord障害でも業務は止まらない） |

## 9. 運用責任者への確認事項（実装前に決めたい）

1. **誰が見られるか**: Admin以上（推奨）でよいか。Editorにも「状態と予算」だけ見せるか。
2. **画面から止めてよいか**（全停止／静か／再開）。止めるだけ（再開はDiscordの`/nul`だけ）にする選択肢もある。
3. **ユーザー別の利用状況**に、Discordの表示名を出してよいか（出さず、件数だけにもできる）。
4. **ノート・要約の本文を管理画面で見せるか**: 初期版は「見せない」（推奨）。見せるなら、閲覧の監査ログと、DM由来のprivateなノートは別扱い（見せない）にする。
5. 通知（§7）を入れるか。入れるなら通知先のチャンネル。
