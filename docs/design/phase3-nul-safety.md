# 第3フェーズ P0: ぬるの安全性・人格・記憶の設計

2026-11-29。対象: `services/agent`。現状は [NUL_OVERVIEW](../NUL_OVERVIEW.md)、判断は [DECISIONS NUL-15](../DECISIONS.md)。**この文書は、依頼（§2.1〜2.5）に対する現状調査・実装した変更・残る課題の記録**。

## 2. 実装した変更（P0）

1. **DM廃止（権限・イベント段階で3層）**: ①Gateway Intentsから`IntentsDirectMessages`を除去（DMイベントがそもそも届かない）。②`convert`が対象サーバー以外（DM含む）を破棄（記録・応答・記憶生成なし）。③`Responder.Decide`がDMを拒否。さらに`/nul`もサーバー外からは無視。テスト: `TestGatewayDropsDMAndForeignGuild`・`TestDecide`。
   - Discord Developer Portal側でBotの「DMを受けない」設定はできない（Intentsで届かなくなる）。ユーザーが先にDMを送ること自体はDiscordの仕様で防げないが、ぬるは何も処理しない。
2. **人格の改訂**: 冷めて自由・ノリがよい・雑談は短い・褒めない励まさない・ぬるぽ→ガッ。固定台詞にしない。会計・個人情報・セキュリティ・団体運営の話は正確に、が線。
3. **プロンプト簡略化**: 固定プロンプトを役割別（人格／線／入力とツール）に再構成して約半分に。ツールの使い方の細則は各ツールの`Description`へ。固定プロンプトに変わるもの（日時・気分・場所・人名）を入れない既存テストは維持。
4. **乱用上限**: リマインダー作成は1人1日10回（`daily_calls.kind='remind'`・migration 00023）。1回の返答のツール呼び出しは総数6回まで（ラウンド3回の上限と併用）。リマインダーに**繰り返し機能は無い**ので、頻度・間隔の乱用経路は無い（有効10件・最大1年先・最短1分後）。管理者も同じ上限。

## 3. プロンプトインジェクション対策の整理（既存＋追加）

層1: **ツールを最小に**（上記10個。会計・Drive・Sheets・デプロイ・SSHは与えない）。層2: **サーバー側の認可**（ユーザーIDは発言者から。LLM出力のIDは使わない）。層3: **量の上限**（予算・1人1日・ラウンド・ツール総数・リマインダー）。層4: **データの隔離**（`untrusted_message`）。層5: **停止**（`/nul stop`・フェイルセーフ）。層6: **自己改善は提案のみ**。

**会計機能とぬるの関係（重要な設計判断）**: 購入申請のAI補助（P2）は**ぬるのDiscord側と別の呼び出し**として実装し、使えるのは「申請の下書きを更新する限定ツール」だけ。**Discord上のぬるには会計ツールを与えない**（Discord投稿経由のインジェクションで申請・承認・Drive/Sheetsが動く経路を作らない）。承認・申請確定・領収書確認は人の操作だけ。

## 4. Discordの権限: Administratorを維持する判断とリスク（2026-11-29 運用責任者の決定）

**決定**: Botの Administrator 権限は当面維持する。**ただし「Botが持つ権限」と「LLMが実行できる操作」を分離する**。

- **分離の仕組み（コードで強制）**: LLMが呼べる操作は、①ツール10個（`TestToolAllowlistIsPinned`で固定。増減はテスト変更＝レビュー対象）と、②ぬるの送信許可リスト（返信・リアクション・入力中・times投稿・依頼者へのリマインダー）だけ。ロール変更・BAN/Kick・チャンネル作成削除・サーバー設定変更・Bot権限変更・任意の大量送信に当たるDiscord APIを呼ぶコードは存在せず、LLMの出力から新しいAPI呼び出しが生成される経路もない。VPS・DB・認証情報に触れるツールも無い。大量送信・大量リマインダーは、1日・1返答・同時の上限（§2）と、異常検知による自動全停止（§5）で止める。
- **残るリスク（Administratorを維持することの意味）**: ①Botトークンが漏れると、攻撃者はサーバー全体を操作できる（LLMとは無関係）。②ぬるのコードの脆弱性・将来の改修ミスで管理系APIが呼ばれると、被害が最大になる。③デベロッパーポータルの管理アカウントの乗っ取り。**緩和**: トークンはVPSの`.env`のみ・ログに出さない・漏えい時はポータルで即再発行（RUNBOOK）。管理系APIを呼ぶコードを足すPRは、DECISIONSの記録と運用責任者の承認が必要。**推奨（任意・今回は実施しない）**: 実際に必要な権限は View Channels・Read Message History・Send Messages・Send Messages in Threads・Add Reactions の5つ（＋スラッシュコマンド登録はアプリ権限）なので、落ち着いたらAdministratorを外して被害の上限を下げる。
- Intentsは `Guilds`・`GuildMessages`・`GuildMessageReactions`・`GuildMembers`（新メンバーへの一言）・`MessageContent`（特権）。DM Intentは廃止。

## 5. 監査・異常検知・緊急停止（実装済み）

- **ツール実行の監査ログ**: `agent.tool_audit`（時刻・発言者ID・チャンネルID・ツール名・成否）。**引数・本文は保存しない**。保持90日（定期の掃除）。管理者はDBで確認（管理画面は設計済みの[nul-admin-dashboard](nul-admin-dashboard.md)）。
- **異常検知と自動停止**: 10分間にツールの拒否・失敗が30件以上 → 自動で全停止（`stopped`）にし、timesに「止まった」と書く。再開は管理者の`/nul resume`だけ。
- **コンテキストの上限**: 直近の会話は最大10件・合計4,000文字（1発言600文字）、いまの発言は3,000文字まで。長い貼り付けでAPI料金を使い切られない。
- 緊急停止: `/nul stop`・`docker stop`（既存）。

## 6. DM由来データの削除（運用責任者の承認済み。本番反映時に実行）

- 起動時に`Store.PurgeDMData`が実行される（冪等）。**対象**: `messages`のkind='dm'・DMチャンネル由来の`notes`と`private`のノート・`private`のリマインダーとDMチャンネル宛のリマインダー・DMチャンネルの`summaries`と`import_progress`。**対象外**: サーバーの通常のメッセージ・ノート・リマインダー（`TestPurgeDMDataRemovesOnlyDMOrigin`）。件数は`settings`の`dm_purge.last`とログ（内容は出さない）に記録する。
- **バックアップに残るデータ**: 既存のDBバックアップ（日次。世代数はRUNBOOK参照）にはDMの内容が含まれ続け、世代の入れ替わりで消える。**即時に消したい場合は、古いバックアップの手動削除が必要**（本番作業のため承認後）。VPS外バックアップは無い。古いバックアップから復元した場合も、起動時の削除が再度働く。
- `api_usage`のchannel_idにDMのIDが残るが、本文ではなく利用量の記録（予算の根拠）。

## 7. 残課題

- 管理画面（監査ログの閲覧）・自動停止時の管理者個別通知（現状はtimesへの投稿とログ）。
- 用途別のAPI予算（会計のAI補助とぬるの会話を分ける）: 上限の値は変更せず、使用額は用途（purpose）つきで既に記録しているので、後から用途別の上限を設定できる構造にする。
